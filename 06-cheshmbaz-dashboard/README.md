# چشم‌باز — داشبورد هوشمند پایش بازار

داشبورد پایش لحظه‌ای بازار ایران و رمزارز؛ قیمت‌ها از منابع واقعی خوانده می‌شوند، در SQLite به سری زمانی تبدیل می‌شوند و از راه یک API نسخه‌دار به رابط کاربری می‌رسند. ساخته‌شده با **Flask + SQLite** و **بدون هیچ کتابخانهٔ نمودار یا زمان‌بند بیرونی** — نمودارها SVG دست‌ساز هستند و زمان‌بند روی threadهای استاندارد کار می‌کند.

> **توجه:** این پروژه یک نمونه‌کار نمایشی است و توصیهٔ سرمایه‌گذاری نیست. داده‌ها از منابع عمومی خوانده می‌شوند و ممکن است با نرخ‌های رسمی بازار اختلاف داشته باشند.

🔗 **لینک زنده:** <sub>پس از دپلوی این‌جا قرار می‌گیرد</sub>

---

## اجرای محلی

```bash
cd 06-cheshmbaz-dashboard
pip install -r requirements.txt

python -m cheshmbaz serve        # → http://127.0.0.1:10000
```

با اجرای `serve`، زمان‌بند روشن می‌شود و بلافاصله یک دور جمع‌آوری واقعی انجام می‌گیرد؛ داشبورد از همان لحظه دادهٔ زنده دارد.

### دستورهای خط فرمان

| دستور | کار |
|---|---|
| `python -m cheshmbaz serve` | اجرای سرویس وب همراه با زمان‌بند (`--port` و `--no-collector` اختیاری) |
| `python -m cheshmbaz collect` | یک دور واکشی واقعی و چاپ گزارش هر منبع (`--force` قرارداد جمع‌آوری را نادیده می‌گیرد) |
| `python -m cheshmbaz evaluate` | یک دور ارزیابی هشدارها و چاپ رخدادها |
| `python -m cheshmbaz check` | آزمون زندهٔ منابع: قیمت هر قلم + تازگی + پوشش |
| `python -m cheshmbaz status` | وضعیت پایگاه داده، حجم فایل و آخرین اجرای منابع |
| `python -m cheshmbaz init-db` | ساخت اسکیما و آینه‌سازی رجیستری دارایی‌ها |

## پوشش دارایی‌ها

۲۲ قلم در چهار دسته. افزودن قلم تازه فقط یک سطر در `cheshmbaz/assets.py` است؛ بقیهٔ لایه‌ها (منبع، ذخیره‌سازی، API، رابط) از همان رجیستری تغذیه می‌شوند.

| دسته | تعداد | اقلام |
|---|---|---|
| طلا | ۳ | طلای ۱۸ عیار، طلای ۲۴ عیار، مثقال طلا |
| سکه | ۵ | سکه امامی، سکه بهار آزادی، نیم‌سکه، ربع‌سکه، سکه گرمی |
| ارز | ۶ | دلار آمریکا، یورو، پوند انگلیس، درهم امارات، لیر ترکیه، یوان چین |
| رمزارز | ۸ | بیت‌کوین، اتریوم، تتر، بایننس‌کوین، سولانا، ریپل، کاردانو، دوج‌کوین |

هر قلم واحد (`تومان` یا `دلار`) و دقت اعشار خودش را دارد؛ مثلاً کاردانو با چهار رقم اعشار و دوج‌کوین با پنج رقم نمایش داده می‌شود تا دارایی زیر یک دلار هرگز «۰ دلار» دیده نشود.

## معماری

معماری لایه‌ای، با یک قاعدهٔ ثابت: **هر عدد باید بداند از کجا آمده و چقدر تازه است.**

```
منبع داده            جمع‌آور              ذخیره‌سازی           سرویس‌ها              لایهٔ وب
─────────           ───────             ──────────           ────────             ────────
tgju.py       →     collector.py   →    quotes     (آخرین)   →   market.py     →   webapp.py
coingecko.py        • تفکیک شکست        readings   (تاریخچه)      alerts.py          ├ templates/
                    • تلاش مجدد         source_runs(سلامت)        charts? نه        ├ static/
                    • محاسبهٔ تغییر     alert_rules/events                            └ /api/v1/*
                    • قرارداد           watchlist
                    • تشخیص تازگی       assets, meta
```

**جریان داده:** منبع → نرمال‌سازی به یک `Quote` یکدست (شامل قیمت، قیمت قبلی، درصد تغییر، زمان مشاهده، منبع و برچسب تازگی) → ثبت در جدول قیمت‌ها و سری زمانی → تجمیع در سرویس بازار (کارت، نمای کلی، بیشترین تغییرها، سری نمودار) → API با پوشش یکدست → رابط.

هیچ لایه‌ای از لایهٔ دیگر عبور نمی‌کند: رابط هیچ‌گاه منبع را مستقیم صدا نمی‌زند و تنها جایی که اجزا به هم وصل می‌شوند `cheshmbaz/context.py` است.

| ماژول | نقش |
|---|---|
| `cheshmbaz/assets.py` | رجیستری دارایی‌ها: اسلاگ، عنوان، دسته، واحد، دقت، منبع |
| `cheshmbaz/core/` | مدل‌های دامنه، خطاهای دامنه، قالب‌بندی فارسی |
| `cheshmbaz/providers/` | کلاینت HTTP با تلاش مجدد و مدارشکن + دو منبع داده |
| `cheshmbaz/storage/` | اسکیمای SQLite و ریپازیتوری‌های قیمت، تاریخچه، منابع، هشدار و دیده‌بان |
| `cheshmbaz/services/` | جمع‌آور، سرویس بازار، موتور هشدار |
| `cheshmbaz/scheduler.py` | دو حلقهٔ پس‌زمینه (جمع‌آوری و ارزیابی هشدار) |
| `cheshmbaz/webapp.py` | کارخانهٔ برنامه، صفحهٔ داشبورد و API نسخه‌دار |

## منابع داده

| منبع | اقلام | چه می‌دهد | چه نمی‌دهد |
|---|---|---|---|
| `call1.tgju.org` | ۱۴ (طلا، سکه، ارز) | قیمت جاری، کمینه/بیشینهٔ روز | **درصد تغییر ندارد** و زمان مشاهدهٔ منبع هم همراه پاسخ نیست |
| `api.coingecko.com` | ۸ (رمزارز) | قیمت، درصد تغییر ۲۴ ساعته، زمان آخرین به‌روزرسانی | — |

دو نکتهٔ مهم که مستقیماً روی رفتار محصول اثر دارند:

- **خوراک tgju ریال است، خروجی تومان.** تقسیم بر ده در لایهٔ منبع انجام می‌شود. اگر این تبدیل جا بیفتد، کل بازار داخلی ده برابر واقعیت نمایش داده می‌شود؛ به همین دلیل یک آزمون اختصاصی روی همین تبدیل وجود دارد.
- **منبع داخلی درصد تغییر نمی‌دهد.** پس هیچ عددی در لایهٔ منبع ساخته نمی‌شود: درصد تغییر اقلام داخلی از **تاریخچهٔ ثبت‌شدهٔ خود همین سرویس** محاسبه می‌شود و اگر مرجعی نباشد، «—» می‌ماند. درصد رمزارز از خود منبع می‌آید و اولویت دارد.

### پایداری شبکه

| مکانیزم | مقدار پیش‌فرض |
|---|---|
| مهلت هر درخواست | ۱۲ ثانیه |
| تعداد تلاش | ۳ بار |
| تأخیر نمایی | ۰٫۶ ثانیه تا ۸ ثانیه |
| مدارشکن (Circuit breaker) | پس از ۴ شکست پیاپی، ۱۲۰ ثانیه کنار گذاشتن منبع |
| شکست جزئی | شکست یک منبع بقیه را متوقف نمی‌کند؛ هر تلاش (موفق یا ناموفق) در جدول سلامت منابع ثبت می‌شود |

## پایگاه داده

SQLite با اسکیمای نسخه‌دار (نسخهٔ ۲) و هشت جدول:

| جدول | محتوا |
|---|---|
| `quotes` | آخرین وضعیت هر قلم: قیمت جاری، قیمت قبلی، زمان آن، درصد و مبنای تغییر، کمینه/بیشینهٔ روز |
| `readings` | سری زمانی خام برای نمودارها (اسلاگ، قیمت، واحد، منبع، زمان مشاهده، زمان واکشی) |
| `source_runs` | سلامت هر منبع در هر اجرا: موفق/ناموفق، تأخیر، تعداد اقلام، متن خطا |
| `alert_rules` | قواعد هشدار: دارایی، شرط، آستانه، وضعیت، یک‌باره‌بودن، بازهٔ خنک‌شدن، مالک |
| `alert_events` | دفتر رخدادها: وقوع و مهارشدن، با قیمت، آستانه، متن پیام و علت مهار |
| `watchlist` | اقلام دیده‌بان هر بازدیدکننده |
| `assets`, `meta` | آینهٔ رجیستری و کلید–مقدارهای داخلی (مثلاً قرارداد جمع‌آوری) |

**قاعدهٔ تازگی:** وضعیت تازگی هنگام *نوشتن* ثابت نمی‌شود، بلکه در هر *خواندن* از سن داده محاسبه می‌شود. آستانه‌ها: تا ۳۰ دقیقه «زنده»، تا ۲ ساعت «تازه»، تا ۲۴ ساعت «کهنه» و بیشتر از آن «منقضی». دادهٔ کهنه و منقضی هرگز به‌عنوان قیمت جاری معتبر شمرده نمی‌شود. نمونه‌های قدیمی‌تر از ۴۰۰ روز در راه‌اندازی هرس می‌شوند.

## API

همهٔ پاسخ‌ها یک پوشش یکدست دارند و هیچ مسیری استثنا بیرون نمی‌دهد:

```json
{ "ok": true,  "data": { }, "error": null }
{ "ok": false, "data": null, "error": { "code": "validation_error", "message": "…", "field": "…" } }
```

| متد و مسیر | کار |
|---|---|
| `GET /health` | سلامت سرویس، آمار پایگاه داده و وضعیت منابع — **هیچ واکشی شبکه‌ای انجام نمی‌دهد** |
| `GET /api/v1` | فهرست مستندات endpointها |
| `GET /api/v1/meta` | رجیستری دارایی‌ها، بازه‌های نمودار، آستانه‌های تازگی، بازهٔ زمان‌بند |
| `GET /api/v1/overview` | نمای کلی بازار: گروه‌ها، کارت‌ها، اقلام شاخص، بیشترین تغییرها، آمار کل |
| `GET /api/v1/digest` | خلاصهٔ سبک برای نوار بالای صفحه |
| `GET /api/v1/assets` | فهرست اقلام با `kind` و صفحه‌بندی (`page`, `page_size`) |
| `GET /api/v1/assets/<slug>` | جزئیات یک قلم + پوشش تاریخچه + وضعیت دیده‌بان |
| `GET /api/v1/assets/<slug>/series` | سری زمانی واقعی با `range=1D\|7D\|30D\|90D` |
| `GET /api/v1/movers` | بیشترین تغییرها با `window=1D\|7D\|30D` و `limit` |
| `GET /api/v1/search` | جست‌وجو روی نام فارسی، نماد و اسلاگ |
| `GET /api/v1/sources` | سلامت منابع: آخرین اجرا، نرخ موفقیت، وضعیت مدارشکن |
| `GET /api/v1/status` | وضعیت سرویس، زمان‌بند و پایگاه داده |
| `GET /api/v1/watchlist` | دیده‌بان بازدیدکننده با کارت‌های تازه |
| `POST /api/v1/watchlist/<slug>` | افزودن/برداشتن قلم (دکمهٔ ستاره) |
| `DELETE /api/v1/watchlist/<slug>` | برداشتن صریح قلم |
| `GET /api/v1/alerts` | قواعد هشدار به‌همراه **فاصله تا آستانه** |
| `POST /api/v1/alerts` | ساخت قاعده (`slug`, `kind`, `threshold`, `one_shot`, `cooldown_seconds`, `note`) |
| `PATCH /api/v1/alerts/<id>` | فعال/متوقف کردن قاعده |
| `DELETE /api/v1/alerts/<id>` | حذف قاعده (دفتر رخدادها می‌ماند) |
| `POST /api/v1/alerts/preview` | پیش‌نمایش: «اگر همین حالا ساخته شود فعال می‌شود؟» |
| `GET /api/v1/events` | دفتر رخدادها با فیلتر قلم و نمایش/پنهان‌کردن مهارشده‌ها |
| `POST /api/v1/collect` | جمع‌آوری دستی (دکمهٔ «واکشی تازه») |
| `POST /api/v1/alerts/evaluate` | ارزیابی دستی هشدارها بدون واکشی تازه |

**اعتبارسنجی و خطاها:** پارامترهای عددی کران‌دار هستند (مقدار کم نامعتبر است، مقدار زیاد بریده می‌شود)، اسلاگ ناشناس `404 unknown_asset` می‌دهد، بدنهٔ نامعتبر JSON پیام با فیلد `body` می‌گیرد، و خطای غیرمنتظره به `500 internal_error` با همان پوشش تبدیل می‌شود — بدون هیچ ردپای پایتون در پاسخ. پاسخ‌های خواندنی با هدر `Cache-Control` کوتاه (۱۰ ثانیه) کش می‌شوند تا فشار روی پایگاه داده کم باشد.

دو endpoint نوشتن (`collect` و `alerts/evaluate`) در صورت تنظیم `CHESHMAZ_ADMIN_TOKEN` هدر `X-Admin-Token` می‌خواهند؛ اگر این متغیر تنظیم نشده باشد باز هستند تا دموی عمومی کار کند.

## رابط کاربری

یک صفحهٔ واحد، تم تیرهٔ «ترمینال مالی»، تمام‌فارسی و بدون هیچ کتابخانهٔ بیرونی (نه Chart.js، نه فونت اینترنتی — وزیرمتن داخل پروژه است).

- **نوار بالای صفحه:** شش قلم شاخص با قیمت، درصد تغییر و برچسب تازگی + ساعت آخرین به‌روزرسانی + جست‌وجو + دکمهٔ واکشی تازه + کلید به‌روزرسانی خودکار.
- **نمودار تاریخی:** SVG دست‌ساز از دادهٔ واقعی پایگاه داده، با چهار بازهٔ ۲۴ ساعت / ۷ روز / ۳۰ روز / ۹۰ روز. اگر بازه‌ای دادهٔ کافی نداشته باشد، نمودار خالی می‌ماند و پیام می‌دهد — هیچ نمودار تزئینی یا دادهٔ ساختگی رسم نمی‌شود.
- **جدول دارایی‌ها:** ۲۲ قلم با فیلتر دسته، قیمت، درصد تغییر ۲۴ ساعته، برچسب تازگی و دکمهٔ ستارهٔ دیده‌بان.
- **بیشترین تغییرها:** صعودی‌ها و نزولی‌ها در سه پنجرهٔ زمانی، فقط از درصدهای واقعی همان پنجره.
- **ستون کنار:** سلامت منابع، دیده‌بان، فرم ساخت هشدار، دفتر رخداد و وضعیت سرویس.
- **جزئیات هر عدد:** منبع، زمان مشاهده، سن داده، مبنای تغییر و وضعیت تازگی روی هر کارت دیده می‌شود.

رابط در عرض‌های موبایل هم بدون سرریز افقی کار می‌کند و به‌صورت خودکار هر چند ثانیه داده را تازه می‌کند.

## زمان‌بند

دو حلقهٔ مستقل روی threadهای daemon — نه برای هر حلقه یک کتابخانهٔ زمان‌بند:

| حلقه | بازهٔ پیش‌فرض | کار |
|---|---|---|
| جمع‌آوری | ۱۸۰۰ ثانیه | واکشی منابع، ثبت قیمت و نمونهٔ تاریخچه |
| ارزیابی هشدار | ۳۰۰ ثانیه | بررسی قواعد فعال روی آخرین قیمت‌ها |

سه محافظ تکرار روی هم کار می‌کنند: قفل درون‌پروسه‌ای (دو دور هم‌زمان نمی‌شوند)، قرارداد در پایگاه داده (چند worker هم‌زمان دوباره نمونه‌برداری نمی‌کنند) و نوسان تصادفی بازه (دو نمونهٔ هم‌زمان دقیقاً روی هم نمی‌افتند). حلقه‌ها با یک تأخیر کوتاه شروع می‌شوند تا healthcheck پیش از همه‌چیز پاسخ بگیرد، و اگر یک دور خطا بدهد حلقه زنده می‌ماند و دور بعد را ادامه می‌دهد.

جلوگیری از ثبت تکراری در سطح داده هم انجام می‌شود: مشاهده‌ای که زمانش از آخرین نمونهٔ ثبت‌شده بزرگ‌تر نباشد نوشته نمی‌شود — به همین دلیل رمزارز که زمان مشاهدهٔ خودش را می‌دهد، در دورهای پشت‌سرهم رکورد تکراری نمی‌سازد.

## هشدارها

مسیر کامل: **کاربر → دارایی → شرط → آستانه → پایش پس‌زمینه → آگاه‌سازی**، با ثبت در SQLite.

سه شرط پشتیبانی می‌شود: بالاتر از قیمت، پایین‌تر از قیمت، و نوسان بیش از درصد مشخص. آستانه‌ها اعتبارسنجی دامنه‌ای دارند (مثلاً آستانهٔ کسری برای دارایی بدون اعشار رد می‌شود).

چهار محافظ که از سیل هشدار جلوگیری می‌کنند:

| محافظ | رفتار |
|---|---|
| دادهٔ نامعتبر | قاعده‌ای روی دادهٔ کهنه یا منقضی ارزیابی نمی‌شود؛ قیمت قدیمی هشدار «الان» نمی‌سازد و در گزارش به‌عنوان «کهنه» فهرست می‌شود |
| بازهٔ خنک‌شدن | هر قاعده پس از وقوع، تا پایان بازه (پیش‌فرض ۶ ساعت) فقط یک آگاه‌سازی می‌فرستد؛ تکرارها با علت ثبت می‌شوند |
| سقف نرخ | بیش از ۱۲ آگاه‌سازی در هر ۵ دقیقه برای یک مالک ثبت نمی‌شود |
| قاعدهٔ یک‌باره | پس از اولین وقوع خودکار متوقف می‌شود |

هر تلاش — موفق یا مهارشده — در دفتر رخداد می‌نشیند، چون پنهان‌کردن مهارشدن‌ها این توهم را می‌سازد که قاعده کار نمی‌کند. دفتر به سقف ۵۰۰۰ رخداد هرس می‌شود و سقف قواعد هر مالک ۲۰۰ است.

## متغیرهای محیطی

| متغیر | پیش‌فرض | کار |
|---|---|---|

## دپلوی روی Render

فایل `render.yaml` (Blueprint) در ریشهٔ همین پوشه است، ولی **در ریشهٔ مخزن نیست** — این نکته در گام ۱ حیاتی است.

### گام ۱ — ساخت سرویس از Blueprint

۱. وارد داشبورد Render شوید → **New** → **Blueprint**.
۲. مخزن `Demos-FA` را وصل کنید.
۳. در فیلد **Blueprint Path** مقدار زیر را بگذارید (Render به‌صورت پیش‌فرض فقط `render.yaml` ریشهٔ مخزن را می‌بیند و بدون این مقدار چیزی پیدا نمی‌کند):

```
06-cheshmbaz-dashboard/render.yaml
```

۴. **Apply** بزنید.

### گام ۲ — تنظیمات سرویس

این مقادیر در Blueprint آمده‌اند و به‌صورت خودکار اعمال می‌شوند:

| تنظیم | مقدار |
|---|---|
| Type | Web Service |
| Runtime | Python |
| Plan | Free |
| Region | Frankfurt |
| Root Directory | `06-cheshmbaz-dashboard` |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `gunicorn cheshmbaz.webapp:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120` |
| Health Check Path | `/health` |

فیلد **Root Directory** در این مخزن چندپروژه‌ای الزامی است؛ بدون آن Render از ریشهٔ مخزن بیلد می‌کند، `requirements.txt` را پیدا نمی‌کند و دپلوی شکست می‌خورد.

### گام ۳ — متغیرهای محیطی

| متغیر | مقدار | توضیح |
|---|---|---|
| `PYTHON_VERSION` | `3.10.20` | باید **کامل و منتشرشده** باشد (`major.minor.patch`)؛ مقدار ناقص مثل `3.10` بیلد را می‌شکند |
| `CHESHMAZ_ENV` | `production` | فعال‌کردن حالت تولید |
| `COLLECT_INTERVAL_SECONDS` | `1800` | بازهٔ جمع‌آوری خودکار |
| `ALERT_PCT` | `2.0` | آستانهٔ پیش‌فرض هشدار نوسان |
| `CHESHMAZ_ADMIN_TOKEN` | *تنظیم نکنید* | با تنظیم آن، دکمهٔ «واکشی تازه» خطای توکن می‌دهد (چون رابط جایی برای واردکردن توکن ندارد). برای دموی عمومی خالی بگذارید |

بقیهٔ متغیرها پیش‌فرض‌های معقول دارند و نیازی به تنظیم ندارند.

### گام ۴ — تأیید دپلوی

پس از پایان بیلد، سلامت سرویس را بررسی کنید:

```bash
curl https://<your-service>.onrender.com/health
```

```json
{
  "ok": true,
  "data": {
    "status": "ok",
    "service": "cheshmbaz-dashboard",
    "environment": "production",
    "engine_ready": true,
    "scheduler": { "running": true, "cycles": 1 },
    "database": { "quotes": 22, "readings": 22, "schema_version": 2 },
    "quotes": 22,
    "providers": [ { "name": "tgju", "last_ok": true } ]
  },
  "error": null
}
```

اگر `quotes` صفر بود، زمان‌بند تازه شروع شده است؛ چند لحظه بعد پاسخ دوباره بگیرید یا یک‌بار `/api/v1/collect` را صدا بزنید. اگر `providers` خطا نشان می‌داد، متن خطا و نرخ موفقیت همان‌جا قابل خواندن است.

### پایداری داده — نیازمند پلن پرداختی

دیسک ماندگار در **پلن رایگان Render قابل اتصال نیست**. در نتیجه `data/cheshmbaz.db` با هر دپلوی از نو ساخته می‌شود و تاریخچهٔ نمودار، قواعد هشدار و دفتر رخداد از دست می‌رود. قیمت‌های تازه بلافاصله بعد از بالا آمدن سرویس دوباره جمع می‌شوند، ولی نمودارهای ۷ روز / ۳۰ روز / ۹۰ روز تا انباشته‌شدن تاریخچه خالی می‌مانند.

برای نگه‌داشتن داده: سرویس را به پلن پرداختی ارتقا دهید، یک دیسک در `/var/data` سوار کنید و دو متغیر زیر را اضافه کنید:

```
CHESHMAZ_DATA_DIR  = /var/data
CHESHMAZ_DB_PATH   = /var/data/cheshmbaz.db
```

### چند نکتهٔ عملیاتی

- **خواب پلن رایگان:** سرویس پس از حدود ۱۵ دقیقه بی‌فعالیتی می‌خوابد و اولین بازدید پس از آن چند ده ثانیه طول می‌کشد. پس از بیدارشدن، زمان‌بند دوباره شروع می‌کند.
- **یک worker:** عامدانه `--workers 1` انتخاب شده است. حلقه‌های زمان‌بند درون همان پروسه اجرا می‌شوند؛ چند worker هم درست کار می‌کند (قرارداد SQLite جلوی نمونه‌برداری موازی را می‌گیرد) ولی بدون دلیل زمان‌بند را چند بار بالا می‌آورد.
- **ساخت دستی سرویس:** اگر Blueprint را نمی‌خواهید، یک Web Service بسازید و همان پنج مقدار گام ۲ را دستی بگذارید؛ در این حالت فیلد Root Directory را هم فراموش نکنید.
- **لاگ‌ها:** در تب **Logs** داشبورد. هر دور جمع‌آوری یک سطر با مدت اجرا و تعداد قیمت‌های ثبت‌شده می‌نویسد.

## محدودیت‌ها

- **درصد تغییر اقلام داخلی تخمینی است، نه رسمی.** tgju درصد تغییر نمی‌دهد؛ این عدد از تاریخچهٔ ثبت‌شدهٔ خود سرویس محاسبه می‌شود. اگر مرجعی نباشد، «—» می‌ماند و هیچ‌وقت صفر جای عدد واقعی گذاشته نمی‌شود. در روز اول کار سرویس، مبنا کوتاه‌تر از ۲۴ ساعت است و مبنای تغییر روی هر کارت اعلام می‌شود.
- **نبود منبع دوم برای بازار داخلی.** اگر tgju قطع شود، هیچ جایگزینی برای طلا و ارز وجود ندارد؛ سیستم این وضعیت را صادقانه «در دسترس نیست» گزارش می‌کند و قیمت قدیمی را به‌جای زنده نشان نمی‌دهد. صفحهٔ سالم می‌ماند و رمزارزها از CoinGecko می‌آیند.
- **نرخ‌محدودی CoinGecko.** نسخهٔ عمومی این API سقف درخواست دارد؛ بازهٔ جمع‌آوری ۳۰ دقیقه‌ای برای دمو امن است ولی برای بار سنگین‌تر به کلید API نیاز است.
- **SQLite و یک نمونه.** این معماری برای یک نمونهٔ سرویس طراحی شده است. برای چند نمونهٔ هم‌زمان، پایگاه داده باید به PostgreSQL و قرارداد جمع‌آوری به یک صف مشترک منتقل شود.
- **نمودارها به تاریخچهٔ انباشته وابسته‌اند.** بازهٔ ۹۰ روزه تا سه ماه دادهٔ واقعی نمی‌دهد نتیجهٔ معناداری ندارد؛ نمودار در این حالت صادقانه خالی می‌ماند.
- **دقت نمایش محدود است.** قیمت‌ها با دقت تعریف‌شده در رجیستری گرد می‌شوند؛ این عدد برای پایش روند است، نه برای تسویه یا حسابداری.
