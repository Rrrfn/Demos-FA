# کارینو — پلتفرم هوش استخدام

کارینو آگهی‌های شغلی را از چند منبع عمومی جمع می‌کند، تکراری‌ها را حذف می‌کند، هر آگهی را با
یک پروفایل تخصصی مقایسه و **امتیازدهی توضیح‌پذیر** می‌کند و در پایان یک پیشنهاد کاری
مدرک‌محور می‌نویسد. ساخته‌شده با **Python 3.10**، **Flask 3**، **SQLite** و stdlib — بدون
هیچ موتور جست‌وجو، سرویس بیرونی یا مدل اجباری.

خط لوله کامل، واقعاً اجرا می‌شود:

```
منابع → واکشی → یکسان‌سازی → حذف تکراری → دسته‌بندی → امتیازدهی → رتبه‌بندی → توضیح → پیشنهاد
```

| مسیر | صفحه |
|---|---|
| `/` | نمای کلی بازار کار و سلامت منابع |
| `/jobs` | همهٔ آگهی‌ها با جست‌وجو، فیلتر و ترتیب |
| `/jobs/<id>` | جزئیات آگهی + تحلیل تطابق «چرا این امتیاز؟» + کارگاه پیشنهاد |
| `/saved` | فهرست ذخیره‌شده |
| `/sources` | سلامت و تاریخچهٔ هر منبع |
| `/activity` | رویدادهای سامانه |
| `/proposal` | کارگاه پیشنهاد |
| `/profile` | پروفایل مهارت‌ها و سبد نمونه‌کار |
| `/health` | سلامت سرویس (برای سامانهٔ پایش میزبان) |

> **توجه:** این پروژه یک نمونه‌کار نمایشی است. آگهی‌ها **واقعی و زنده** از منابع عمومی
> هستند، ولی «پروفایل» یک نمونهٔ فرضی برای نمایش کیفیت موتور تطبیق است؛ آگهی‌ها به آن
> پروفایل ارسال نشده‌اند و هیچ ادعایی دربارهٔ آن‌ها مطرح نمی‌شود.

## اجرای محلی

نیازمندی: Python 3.10 یا بالاتر.

```bash
cd 07-karino-ai-agent
python -m venv .venv
source .venv/bin/activate        # ویندوز: .venv\Scripts\activate
pip install -r requirements-dev.txt
```

سه فرمان وجود دارد:

```bash
python -m karino check      # بررسی سلامت پیکربندی، پروفایل و پایگاه داده
python -m karino ingest     # یک دور جمع‌آوری، بدون بالا آوردن سرور
python -m karino serve      # وب‌سرور + زمان‌بند پس‌زمینه (پیش‌فرض)
```

- `http://127.0.0.1:10000` داشبورد
- `http://127.0.0.1:10000/health` سلامت سرویس

پایگاه دادهٔ SQLite در نخستین اجرا در `data/karino.db` ساخته می‌شود. برای دیدن داشبورد پر،
اول یک دور جمع‌آوری بزنید:

```bash
python -m karino ingest
python -m karino serve --no-scheduler
```

| پرچم `serve` | کار |
|---|---|
| `--port 8080` | تغییر پورت |
| `--host 127.0.0.1` | محدود کردن به میزبان محلی |
| `--no-scheduler` | خاموش کردن جمع‌آوری دوره‌ای |
| `--debug` | حالت اشکال‌زدایی Flask |

| `KARINO_LLM_KEY` | خالی | کلید مدل |
| `KARINO_LLM_MODEL` | `gpt-4o-mini` | نام مدل |
| `KARINO_ADMIN_TOKEN` | خالی | اگر پر شود، endpointهای نوشتن API هدر `X-Admin-Token` می‌خواهند |

## معماری

هر لایه فقط چیزی را می‌بیند که لازم دارد؛ هیچ ماژولی مستقیم `os.environ` نمی‌خواند و هیچ
قالبی عدد حساب نمی‌کند.

```
karino/
  config.py          تنظیمات بی‌تغییر، یک‌بار خوانده‌شده از محیط
  core/              خطاهای دسته‌بندی‌شده، مدل‌های دامنه، ابزارهای متن فارسی
  profile.py         تنها منبع حقیقت: مهارت‌های وزنی، ترجیحات، سبد نمونه‌کار
  sources/           یک آداپتور مستقل برای هر منبع + کلاینت HTTP مقاوم
  pipeline/          normalize → dedupe → scoring → proposal
  storage/           طرح‌وارهٔ SQLite و مخازن (آگهی، امتیاز، پیشنهاد، ذخیره، منابع، فعالیت)
  services/          خط لولهٔ جمع‌آوری، تحلیل و تجمیع، سرویس پیشنهاد
  web/               صفحات سمت سرور، API نسخه‌دار، لایهٔ نمایش فارسی
  scheduler.py       حلقهٔ پس‌زمینه با تک‌نمونه‌ای و بدون هم‌پوشانی
  webapp.py          کارخانهٔ اپ + نقطهٔ ورود WSGI
```

### جریان داده

1. **واکشی** — هر کانکتور مستقل دادهٔ خودش را می‌گیرد. خطای یک منبع فقط در گزارش منابع
   و صفحهٔ فعالیت ثبت می‌شود؛ بقیه بی‌وقفه ادامه می‌دهند.
2. **یکسان‌سازی** — HTML پاک می‌شود، دورکاری از سه سیگنال (پرچم منبع، محل، متن) تعیین
   می‌شود، نوع همکاری به کلیدهای استاندارد نگاشته می‌شود و یک انگشت‌نگاشت
   *مستقل از منبع* (عنوان + کارفرما) ساخته می‌شود.
3. **حذف تکراری** — دو سطح: انگشت‌نگاشت یکسان (یک آگهی در دو منبع) و شباهت عنوان
   (تفاوت‌های جزئی مثل پسوند «(Remote)»). برندهٔ گروه «کامل‌ترین» رکورد است و کمبودهایش
   از رکورد بازنده پر می‌شود، تا بودجه یا تاریخ از دست نرود.
4. **امتیازدهی** — نُه عامل با مجموع سقف دقیقاً ۱۰۰؛ هر عامل مدرک و توضیح خودش را
   برمی‌گرداند و نتیجه کامل (نه فقط عدد) ذخیره می‌شود.
5. **ذخیره و رتبه‌بندی** — فیلتر، جست‌وجو، صفحه‌بندی و ترتیب همه در SQL بسته می‌شوند،
   نه در پایتون.

### منابع داده

| منبع | نوع | داده |
|---|---|---|
| جاب‌ویژن | RSS | آگهی‌های فارسی ایران |
| Remotive | JSON API | موقعیت‌های دورکاری |
| RemoteOK | JSON API | موقعیت‌های دورکاری |
| Arbeitnow | JSON API | موقعیت‌های اروپا/آلمان |
| We Work Remotely | RSS | موقعیت‌های دورکاری |
| Hacker News (Who is hiring) | RSS | استخدام‌های استارتاپی |
| فیدهای دلخواه | RSS | هر فید عمومی که با `JOB_FEED_URLS` معرفی شود |

هیچ صفحهٔ HTML اسکرپ نمی‌شود و هیچ هدر جعلی مرورگر فرستاده نمی‌شود؛ فقط فید و API عمومی.
افزودن منبع تازه = نوشتن یک کلاس کانکتور و افزودن آن به `sources/REGISTRY`.

### پایگاه داده

شش جدول: `jobs`، `scores`، `proposals`، `saved`، `source_runs`، `activity`.
حالت WAL و `timeout` روشن است تا خواندن هم‌زمان با نوشتن زمان‌بند قفل نخورد.
`jobs` روی `(source, external_id)` قید یکتایی دارد و درج، بازیابی امن در برابر مسابقه
دو کارگر را انجام می‌دهد.

## موتور تطبیق و «چرا این امتیاز؟»

امتیاز از نُه عامل ساخته می‌شود؛ مجموع سقف‌ها دقیقاً ۱۰۰ است (تست این را قفل می‌کند):

| عامل | سقف | چه چیزی را می‌سنجد |
|---|---|---|
| تطبیق مهارت | ۴۰ | سهم وزنی مهارت‌های منطبق از یک هدف واقع‌بینانه (۴۲) |
| تخصص اصلی در عنوان | ۱۰ | حضور تخصص اصلی (وزن ۸+) در عنوان آگهی |
| سطح ارشدیت | ۱۰ | هم‌خوانی سطح آگهی با سطح هدف |
| نوع همکاری | ۱۰ | هم‌راستایی با نوع همکاری ترجیحی |
| تازگی آگهی | ۹ | تازگی بر پایهٔ تاریخ انتشار |
| دورکاری | ۸ | ترجیح کار از راه دور |
| شفافیت بودجه | ۶ | اعلام‌شدن بازهٔ بودجه |
| محل کار | ۴ | محدودهٔ جغرافیایی مطلوب |
| نشانه‌های کارفرمای جدی | ۳ | نام کارفرما، شرح مفصل، لینک مرجع، برچسب‌های متنوع |

هر عامل `points`، `max_points`، `detail` و `evidence` دارد. صفحهٔ آگهی همان‌ها را رندر می‌کند،
مثلاً برای یک آگهی با امتیاز **۸۵ (تطابق عالی)**:

```
تطبیق مهارت            ۳۷.۱ / ۴۰   ← طراحی REST API (وزن ۹)، دیتابیس SQL (وزن ۷) …
تخصص اصلی در عنوان      ۶.۵ / ۱۰
سطح ارشدیت             ۱۰   / ۱۰
نوع همکاری             ۱۰   / ۱۰
تازگی آگهی              ۰   / ۹    ← منتشرشده ۲۸ روز پیش
شفافیت بودجه            ۶   / ۶
دورکاری                 ۸   / ۸
محل کار                 ۴   / ۴
نشانه‌های کارفرمای جدی   ۳   / ۳    ← ۵ نشانه از ۵ نشانه
```

فهرست «دلایل» بر پایهٔ **سهم ازدست‌رفته** مرتب می‌شود، نه ترتیب ثابت: کاربر اول می‌بیند
کدام عامل کم آورده. آستانهٔ برچسب: زیر ۵۵ ضعیف · ۵۵–۷۱ متوسط · ۷۲–۸۴ قوی · ۸۵+ عالی.

### پیشنهادنویس

پیشنهاد سه بخش دارد و هر بخش از دادهٔ همان آگهی تغذیه می‌شود: **قلاب** (مهم‌ترین مهارت‌های
متقابل)، **مدرک** (نمونه‌کارهایی که *مهارت‌های منطبق همان آگهی* را پوشش می‌دهند — پویا،
نه فهرست ثابت) و **روش کار**. سه لحن (رسمی، کوتاه، مشورتی) و دو طول (استاندارد، کوتاه).

اگر `KARINO_LLM_URL` تنظیم شده باشد، همان پیش‌نویس به مدل داده می‌شود و نسخهٔ روان‌ترش
برمی‌گردد؛ ولی هر خطای شبکه، سهمیه یا ساختار پاسخ **بی‌صدا** به پیش‌نویس قاعده‌محور
برمی‌گردد. یعنی سامانه بدون هیچ مدلی کامل کار می‌کند.

## API

همه زیر `/api/v1` و با یک قالب پاسخ یکدست:

```json
{ "ok": true,  "data": "…", "meta": { } }
{ "ok": false, "error": { "code": "invalid_request", "message": "…", "detail": "…" } }
```

| متد | مسیر | کار |
|---|---|---|
| GET | `/api/v1/health` | سلامت نسخه‌دار (با پوشش) |
| GET | `/api/v1/overview` | اعداد کلیدی، توزیع امتیاز، سلامت منابع |
| GET | `/api/v1/profile` | مهارت‌های وزنی و سبد نمونه‌کار |
| GET | `/api/v1/jobs` | فهرست با `q`، `min`، `max`، `source`، `remote`، `saved`، `sort`، `page`، `per_page` |
| GET | `/api/v1/jobs/<id>` | جزئیات + تحلیل تطابق کامل |
| GET | `/api/v1/jobs/<id>/match` | فقط تحلیل تطابق |
| POST | `/api/v1/jobs/<id>/rescore` | امتیازدهی دوباره با پروفایل فعلی |
| GET | `/api/v1/jobs/<id>/proposal` | خواندن پیشنهاد (با `tone` و `variant`) |
| POST | `/api/v1/jobs/<id>/proposal` | ساخت پیشنهاد (کلید `force` کش را نادیده می‌گیرد) |
| GET | `/api/v1/saved` | فهرست ذخیره‌شده |
| POST / DELETE | `/api/v1/jobs/<id>/save` | افزودن / برداشتن از ذخیره‌شده |
| GET | `/api/v1/sources` | سلامت و نرخ موفقیت هر منبع |
| GET | `/api/v1/activity` | رویدادها با فیلتر `level` |
| POST | `/api/v1/ingest` | اجرای یک دور جمع‌آوری (ورودی اختیاری `sources`) |

`/health` بدون پیشوند و بدون پوشش است، چون سامانهٔ پایش میزبان شکل ثابتی از آن انتظار دارد:

```json
{ "database": "ok", "env": "production", "jobs": 261, "score_budget": 100.0,
  "service": "karino-ai-agent", "sources": 7, "status": "ok", "version": "1.0" }
```

خطاها کد ماشین‌خوان می‌گیرند (`invalid_request`، `not_found`، `unauthorized`، …) و
اعتبارسنجی واقعی است: پارامتر عددی نامعتبر، بازهٔ `min`/`max` وارونه، منبع ناشناخته،
ترتیب پشتیبانی‌نشده و مقدار بولی نامعتبر همه ۴۰۰ می‌گیرند.

اگر `KARINO_ADMIN_TOKEN` تنظیم شود، فقط **نوشتن‌های API** هدر `X-Admin-Token` می‌خواهند.
رابط داشبورد از مسیرهای صفحه استفاده می‌کند، پس دمو بدون توکن هم با یک کلیک کار می‌کند.

## خودکارسازی

زمان‌بند یک ریسهٔ سادهٔ پایتون است، نه APScheduler: تنها کار لازم «هر N دقیقه یک تابع»
است. دو محافظ دارد: **تک‌نمونه‌ای** (دوبار `start` ریسهٔ دوم نمی‌سازد) و **بدون هم‌پوشانی**
(اگر یک دور طول بکشد، دور بعدی پشت آن منتظر می‌ماند). خطای یک دور، ریسه را نمی‌کشد و
رخداد آن در صفحهٔ فعالیت ثبت می‌شود. راه‌اندازی نیز یک‌بار در هر پروسه انجام می‌شود.

## اجرای تولید

```bash
gunicorn karino.webapp:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120
```

`karino.webapp:app` نقطهٔ ورود WSGI است و همان کارخانهٔ اپ را در راه‌اندازی صدا می‌زند؛
پس پایگاه داده، دور نخست جمع‌آوری و زمان‌بند زیر gunicorn هم درست بالا می‌آیند.

**یک worker** عامدانه انتخاب شده است: زمان‌بند و خط لوله داخل خود پروسهٔ وب زندگی می‌کنند
و با چند worker، هر کدام منبع خودش را واکشی می‌کند. اگر لازم شد بیش از یک worker اجرا شود،
`ENABLE_SCHEDULER=0` را تنظیم کنید تا هر worker زمان‌بند خودش را نسازد.

## دپلوی روی Render

دپلوی این پروژه سه نکتهٔ تعیین‌کننده دارد که اگر رعایت نشوند شکست می‌خورد:

1. **Root Directory الزامی است.** این پروژه داخل یک مخزن چندپروژه‌ای (`Demos-FA`) است؛ اگر
   Render از ریشهٔ مخزن بیلد کند، `requirements.txt` را پیدا نمی‌کند و build شکست می‌خورد.
2. **فایل blueprint در ریشهٔ مخزن نیست** و در `07-karino-ai-agent/render.yaml` قرار دارد، پس
   هنگام ساخت Blueprint باید مسیر آن صریحاً داده شود.
3. **یک worker کافی و لازم است** (دلیلش در بخش «اجرای تولید» آمد).

### پیش‌نیاز

- مخزن روی GitHub و دسترسی Render به آن
- پلن رایگان Render کافی است؛ محدودیت‌های آن پایین‌تر توضیح داده شده

### گام ۱ — ساخت سرویس از Blueprint

1. در داشبورد Render: **New +** → **Blueprint**
2. مخزن `Demos-FA` را انتخاب کنید
3. در فیلد **Blueprint Path** مقدار `07-karino-ai-agent/render.yaml` را وارد کنید
   (Render به‌صورت پیش‌فرض فقط `render.yaml` در ریشهٔ مخزن را می‌بیند)
4. **Apply** را بزنید

Render سرویس را با این تنظیمات می‌سازد:

| تنظیم | مقدار |
|---|---|
| نوع | Web Service (Python) |
| Root Directory | `07-karino-ai-agent` |
| Build Command | `pip install -r requirements.txt` |
| Start Command | `gunicorn karino.webapp:app --bind 0.0.0.0:$PORT --workers 1 --threads 4 --timeout 120` |
| Health Check Path | `/health` |
| Plan | Free |

### گام ۲ — تنظیم متغیرهای محیطی

این‌ها را `render.yaml` خودش تنظیم می‌کند:

| متغیر | مقدار |
|---|---|
| `PYTHON_VERSION` | `3.10.20` |
| `KARINO_ENV` | `production` |
| `KARINO_COLLECT_ON_BOOT` | `1` — یک دور جمع‌آوری در راه‌اندازی تا سرویس خالی بالا نیاید |
| `FETCH_INTERVAL_MIN` | `360` — جمع‌آوری دوره‌ای هر ۶ ساعت |
| `KARINO_SEED_DEMO` | `0` — هیچ آگهی نمونه‌ای ساخته نمی‌شود |
| `KARINO_LLM_URL` / `KARINO_LLM_KEY` | خالی (اختیاری؛ از داشبورد پر کنید) |
| `KARINO_ADMIN_TOKEN` | خالی (اختیاری؛ دموی عمومی با یک کلیک کار می‌کند) |

> `PORT` را دستی تنظیم **نکنید**؛ Render آن را خودش تزریق می‌کند و هم `config.py` و هم
> دستور start از همان می‌خوانند.

دو نکتهٔ عملی در دپلوی:

- **دور نخست جمع‌آوری چند ثانیه طول می‌کشد** (شش منبع، هر کدام تا ۶۰ آگهی). سرویس در همین
  زمان بالا می‌آید و صفحهٔ `/health` بی‌درنگ پاسخ می‌دهد؛ داده چند ثانیه بعد پدیدار می‌شود.
- **دیسک پلن رایگان به سرویس وصل نمی‌شود**، پس `data/karino.db` با هر دپلوی از نو ساخته
  می‌شود و تاریخچه و قاعده‌های ذخیره‌شده از بین می‌روند. برای پایداری، سرویس را ارتقا دهید،
  دیسکی روی `/var/data` سوار کنید و `KARINO_DATA_DIR=/var/data` را تنظیم کنید (نمونه‌اش در
  `render.yaml` کامنت شده است).

### گام ۳ — تأیید دپلوی

پس از پایان build، آدرس سرویس به شکل `https://<نام-سرویس>.onrender.com` خواهد بود
(نام سرویس در blueprint برابر `karino-ai-agent` است). سلامت سرویس را بپرسید:

```bash
curl -s https://karino-ai-agent.onrender.com/health
```

پاسخ درست:

```json
{
  "database": "ok",
  "env": "production",
  "jobs": 261,
  "score_budget": 100.0,
  "service": "karino-ai-agent",
  "sources": 7,
  "status": "ok",
  "version": "1.0"
}
```

### گام ۴ — بررسی سریع پس از دپلوی

```bash
# فهرست آگهی‌ها
curl -s "https://karino-ai-agent.onrender.com/api/v1/jobs?per_page=3"

# تحلیل تطابق یک آگهی
curl -s https://karino-ai-agent.onrender.com/api/v1/jobs/1/match

# سلامت منابع (کدام منبع در دپلوی پاسخ نداده)
curl -s https://karino-ai-agent.onrender.com/api/v1/sources
```

اگر `jobs` صفر ماند، یعنی هیچ منبعی از دیتاسنتر به بیرون دسترسی نداشته است؛ صفحهٔ
`/sources` علت هر منبع را نشان می‌دهد و `/activity` هم همان را ثبت کرده است. سامانه در این
حالت آگهی جعلی نمی‌سازد.

### اجرای دوبارهٔ جمع‌آوری روی سرویس دپلوی‌شده

دکمهٔ «جمع‌آوری تازه» در نوار بالای داشبورد (فرم `POST /collect`) همین کار را می‌کند. با API:

```bash
curl -s -X POST https://karino-ai-agent.onrender.com/api/v1/ingest \
     -H 'Content-Type: application/json' -d '{"sources": ["remotive"]}'
```

اگر `KARINO_ADMIN_TOKEN` تنظیم شده باشد، این درخواست هدر `X-Admin-Token` می‌خواهد.

## محدودیت‌های شناخته‌شده

- **پروفایل فرضی است.** امتیازها بازتاب یک نمونهٔ نمایشی‌اند، نه یک جست‌وجوی واقعی کار.
- **رمزارز/ارز پوشش داده نمی‌شود.** فقط منابع شغلی.
- **پارامترهای دسته‌بندی بعضی APIها نادیده گرفته می‌شوند** (بررسی شده در Remotive و
  جاب‌ویژن)، پس بخشی از آگهی‌ها به تخصص پروفایل مربوط نیستند و امتیاز پایین می‌گیرند. این
  عمداً پنهان نمی‌شود: توزیع امتیاز در نمای کلی همین را نشان می‌دهد.
- **شباهت عنوان بر پایهٔ واژه است، نه معنایی.** «Python Developer 1» و «Python Developer 2»
  از یک کارفرما در هم ادغام می‌شوند، چون توکن‌های تک‌حرفی در محاسبهٔ شباهت نادیده می‌مانند.
- **پایگاه داده روی پلن رایگان موقتی است** (توضیحش در بخش دپلوی آمد).
- **تاریخچهٔ سری زمانی در سطح آگهی است، نه قیمت**؛ کارینو نمودار روند ندارد چون دادهٔ
  آن را ندارد و نمودار تزئینی نمی‌سازد.
